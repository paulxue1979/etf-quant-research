# ETF Quant Research System v1.4.2

## Highlights

- Added a local stdio MCP bridge for Codex to inspect Strategy identities,
  Drafts, Regime structure, semantic targets, validation and data availability.
- Added typed, semantic Draft ChangeSet proposals with a human-readable
  before/after diff. Preparation never modifies the Draft.
- Added browser-only human Approve/Reject. Approval replays the exact persisted
  operations, checks Draft revision and hash, re-validates canonically, and
  applies the Draft and decision audit in one transaction.
- Added terminal, reloadable `FAILED` evidence for an attempted application
  that did not modify the Draft. A failed proposal cannot be approved again.
- Approved Draft changes persist across restart without automatically creating
  a StrategyVersion.

## Codex Operator Security Model

Codex permissions in v1.4.2 are **READ** and **PREPARE**. The local MCP registry
does not expose Draft apply, version creation, Backtest, Grid, Experiment,
candidate selection, Freeze, Official OOS, deletion, raw SQL, shell, arbitrary
Python, filesystem write or generic HTTP tools. Only a human using the local
ETF Quant browser UI can approve a persisted ChangeSet. The existing local
browser Origin guard is not a remote identity/authentication model.

The MCP transport is local stdio; there is no public endpoint or tunnel. ETF
Quant's backend does not call the OpenAI API and does not require
`OPENAI_API_KEY`. MCP capability is additive: the core product remains usable
without the MCP bridge.

## Approval Semantics

- Prepare: zero Draft side effects; a typed, bounded proposal is persisted.
- Reject: the Draft remains unchanged.
- Approve: revision and hash must match; semantic operations are resolved
  again; the resulting strategy is validated again; Draft revision increments
  once with a matching decision audit. Duplicate approval is idempotent.
- Stale: a changed Draft cannot silently merge an old proposal.
- Failed: after a human application attempt fails validation, operation
  resolution or the Draft transaction, and no successful commit exists, a
  terminal failure record is written. The Draft remains unchanged. Successful
  approval evidence always remains `APPLIED`, even if a later response fails.

## ChangeSet Lifecycle

`PROPOSED` is the initial persisted proposal. `REJECTED` is an explicit human
decision. `APPLIED` is projected from committed approval evidence. `STALE` is
projected from the current Draft revision/hash. `FAILED` is projected from a
separate, additive failure record. Contradictory success and failure evidence
is an integrity error, not an arbitrary status choice. `FAILED` proposals are
excluded from pending approvals; users must ask Codex to prepare a new one.

## Compatibility

V1.4.2 does not change V1.4.1 strategy semantics, HOLD_PREVIOUS, Peak Drawdown
entry-only behavior, Official OOS all-time-to-date indicator context, Backtest,
Experiment, human Selection, Freeze, Official OOS or Data Availability. Existing
historical StrategyVersion hashes and the V1.4 canary remain unchanged.

## Known Limitations

- Codex cannot directly apply ChangeSets, create versions, or run Backtest,
  Experiment, Grid or Official OOS workflows.
- No remote identity/authentication model; approval is local-application-only.
- A failed ChangeSet is terminal. Reuse requires a fresh proposal from the
  current Draft.
